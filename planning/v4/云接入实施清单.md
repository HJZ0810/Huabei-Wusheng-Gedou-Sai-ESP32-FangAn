从现有成功日志读取的 V3 数值如下，属于 V3 历史编译证据，不代表 V4：

| 构建 | 程序容量 | 静态 RAM | 备注 |
| --- | ---: | ---: | --- |
| core2 2.0.17 | 946,613 / 3,145,728 bytes | 51,668 / 327,680 bytes | 16 MB Flash 配置，3 MB APP 分区 |
| core3 3.3.12 | 1,128,500 / 1,310,720 bytes | 53,192 / 327,680 bytes | 默认 4 MB Flash、默认 APP 分区，PSRAM 未启用 |

core3 默认 APP 仅剩 **182,220 bytes**。TLS 与自主算法的新增量必须以实际链接结果计算，不能沿用 V3 的“默认分区通过”。如果超过默认分区，可明确选择本机 `boards.txt` 已存在的 `esp32:esp32:esp32s3:PartitionScheme=huge_app`：4 MB Flash、3 MB APP、无 OTA。选择更大 APP 不等于确认板载 Flash 型号，也不能同时承诺 OTA；原来的 16 MB PlatformIO 配置仍需真实板型匹配。

静态 RAM 剩余不等于运行时堆余量。TLS 握手、WebSocket 帧、JSON、网络任务栈都需动态内存；后续遥测建议加入当前自由堆、最小自由堆、最大连续空闲块。软件编译不能替代板端握手峰值和控制周期测量。

## 2. 云客户端候选依赖

接口候选为 **Links2004 / WebSockets**；已发布基线 2.7.2 不能直接作为最终双核心安全版本，下面的超时单位差异必须处理。查询时 master 的 `library.properties` 为 2.7.3，但 GitHub 标签列表最新为 2.7.2；两者不能混为“已发布稳定版本”。2.7.2 标签对应提交 `8d0744eb5e916ec646d83bd1ffed5f643aab04d8`。[发布说明](https://github.com/Links2004/arduinoWebSockets/releases/tag/2.7.2)、[固定版本属性](https://github.com/Links2004/arduinoWebSockets/blob/2.7.2/library.properties)。

发布基线的 PlatformIO 条目为 `links2004/WebSockets@2.7.2`，仅适合检查接口，不应忽略下述补丁原样交付。Arduino ZIP 包内库名为 `WebSockets`，须保留原 LGPL 2.1 许可证。库的 ESP32 分支使用 `WiFiClientSecure`，具备 PEM CA 接口及 core 3.0.4 起 bundle 参数变化的分支。**V4 尚未实际编译，不应写成“兼容性已验证”。**[固定头文件](https://github.com/Links2004/arduinoWebSockets/blob/2.7.2/src/WebSocketsClient.h)、[网络实现](https://github.com/Links2004/arduinoWebSockets/blob/2.7.2/src/WebSockets.h)。

**核心 2 的超时单位问题已在源码层确认。**2.7.2 会调用 `_client.tcp->setTimeout(5000)`，但本机 core2 的 `WiFiClient` / `WiFiClientSecure::setTimeout(uint32_t seconds)` 按秒计算，core3 按毫秒处理。因而同一值可能成为 5,000 秒，而不是 5 秒；双核心编译通过也不能发现这个运行问题。固定上游提交 `0013395c755ce16df9d61d46869407d9e07b666d` 已在 core2 分支定义 `NETWORK_SET_TIMEOUT_IN_SECONDS` 并除以 1,000，还允许通过编译参数覆盖消息最大大小。[修正后的客户端](https://github.com/Links2004/arduinoWebSockets/blob/0013395c755ce16df9d61d46869407d9e07b666d/src/WebSocketsClient.cpp)、[修正后的网络头](https://github.com/Links2004/arduinoWebSockets/blob/0013395c755ce16df9d61d46869407d9e07b666d/src/WebSockets.h)。

实施时二选一：优先尝试固定以上完整上游提交，其 `library.properties` 版本是 **2.7.3，尚无正式发布标签**；若必须采用发布标签，则使用 2.7.2 加精确、可审计的 core2 超时单位补丁，保留原提交、补丁文件和 SHA256。两条路线均需双核心实际编译和超时模型回归，禁止用浮动 master 或把补丁库冒充未经修改的官方库。core2 TLS 默认握手超时为 120 秒，另需显式约束握手等待；仅修复 TCP timeout 不够。

拟用接口为 `WebSocketsClient::beginSslWithCA(host, port, path, caPem, protocol)`、`onEvent()`、`setExtraHeaders()`、`setReconnectInterval()`、`loop()`。设备认证头由配置在运行时生成，禁止放进 URL。`enableHeartbeat()` 只用于传输连通性检测，不能替代操作者应用心跳或固件运动租约。[接口声明](https://github.com/Links2004/arduinoWebSockets/blob/2.7.2/src/WebSocketsClient.h)。

**证书空值必须在项目层拒绝。**库在无 CA、无 bundle、无指纹的 ESP32 SSL 分支会调用 `setInsecure()`。因此不能用省略 CA 的 `beginSSL()` 当作安全 WSS；即使调用 `beginSslWithCA()`，也须先验证 CA 非空、格式合理且寿命覆盖连接，保持 CA 缓冲区在整个连接期间有效。无有效 CA 或时间未就绪则不上云，AP 继续工作并显示故障。[固定实现](https://github.com/Links2004/arduinoWebSockets/blob/2.7.2/src/WebSocketsClient.cpp)。

首版建议只用 PEM CA，暂不采用 core2/core3 参数不同的 bundle 接口。公共根证书可以作为受审计的 `cloud_ca.h` 收录；服务器证书私钥绝不能进入固件或工程包。域名与签发链确定后再选择根 CA；不能预设某 CA 对所有服务器有效。启用 SNTP 并等待合理时间后才尝试 TLS，证书或主机名错误不得降级为不校验连接。

库默认 TCP 超时为 5,000 ms，ESP32 最大数据大小为 15 KB；这既不是控制响应保证，也不是项目协议允许的包长。云任务独立于控制任务；应用层限定小命令包，超限拒绝，避免配置巨包、碎片积累和握手阻塞进入控制路径。若需统一修改库级宏，必须同时覆盖 PlatformIO 和 Arduino CLI 的库编译选项；只在草图里定义宏并不能保证单独编译的库收到相同设置。[实现边界](https://github.com/Links2004/arduinoWebSockets/blob/2.7.2/src/WebSockets.h)。

不建议为此引入 Socket.IO、MQTT 客户端或直接依赖尚未在 Arduino 双核心交付里接入的 `esp_websocket_client`。原生 WS 协议与 Node `ws` 足够完成当前需求；Node 端使用受支持 LTS、固定版本 `ws` 和 `package-lock.json`，版本在实际实现时查验并锁定，不把未安装的新依赖写成当前已验证。

## 3. 需要改动的工具与白名单

### 3.1 依赖交付

- `combatbot/platformio.ini`：新增固定提交或有来源清单的 WebSockets 客户端依赖，不能用浮动 master；若选择 2.7.2 必须携带上述安全补丁。
- `combatbot/scripts/package_delivery.py`：三个库的硬编码版本表改为统一清单读取，验证 WebSockets 的 `library.properties` 后打包。
- `combatbot/scripts/verify_delivery.py`：验证第四个 ZIP 的 CRC、版本、许可证存在及哈希；校验 VERSION、发布说明和当前包名。
- `安装Arduino依赖.ps1`：新增 WebSockets，并识别 `src/WebSocketsClient.h` / `src/WebSockets.h` 的旧版重复安装目录；继续先核验全部 ZIP 再备份旧库。
- `Arduino依赖库/WebSockets-<最终版本>.zip`：只来自固定提交或经审计补丁后的依赖解析目录，保留许可证和来源/补丁清单；不要将整个主机 `.pio` 收录到 ZIP。
- 建议新增 `依赖版本.json` 作为脚本共用来源，减少 PlatformIO/安装器/打包器版本漂移；须校验三个使用者与清单一致。

当前本机 Arduino 用户库没有 WebSockets。正式验证可将四个交付库解压到 `combatbot/test-artifacts/v4-arduino-user/libraries/`，传入 `verify_arduino_cli.py --user-dir`。`verify_release.py` 需要增加透传该参数的选项；既不安装全局库，也不能默默依赖其他机器预装版本。

### 3.2 网页与服务端

- `combatbot/web/index.html`：保留单文件 AP 源，新增明确区分本地/云端的 transport 和公网连接状态；云端页面不请求设备的 `192.168.4.1`。
- 新增云网页生成脚本：从同一 HTML 源导出服务器静态文件，加入公共运行参数，参数不得含密码/设备密钥；对导出文件做逐字节/manifest 验证。
- `combatbot/test/ui_contract.mjs`：现有测试只提取 `<script>` 内联块并用 Node VM 执行；如果将网页拆成外部模块，应同步适配加载器，不能保留旧测试造成假通过。首版继续单文件可降低工具链改动。
- 新增 `server/package.json`、`package-lock.json`、源码、真实中继集成测试、启动说明、`.env.example`、反向代理/容器示例；正式 `.env`、TLS 私钥、运行期设备凭据、访问会话、日志、`node_modules` 不进包。
- 包装采用明确文件白名单；不能对 `server/` 全目录 `rglob` 后只排除 `.exe`，否则真实设备凭据可能误打包。当前 `.gitignore` 的 `.env.*` 会同时忽略 `.env.example`，需要精确允许经过审阅的示例文件。

### 3.3 验证凭据

- `verify_release.py`：新增真实云协议模型测试、云会话/命令期限测试、Node 中继集成、云页面回归；每一步成功日志纳入新凭据。
- `release_evidence.py`：扩展源清单到新增根目录输入，并在 required checks 中要求云协议与中继等检查。服务端改动、依赖锁文件改动必须使旧凭据失效。
- `verify_arduino.py` / `verify_arduino_cli.py`：加强导出文件集合一致性；核验两代核心及第四个库的实际版本。若切换分区，要另存明确的构建名称/FQBN，不能把 Huge APP 编译包装成默认分区通过。
- `package_delivery.py` / `verify_delivery.py`：新目录源文件、锁文件、服务端包、公共 CA、日志必须与新 manifest 对应。当前 `源码SHA256.json` 只覆盖草图平铺文件；建议增加整个交付白名单的独立清单，避免误以为它已覆盖服务器。

云测试至少覆盖错误认证、按设备隔离、旁观者越权、旧启动/连接/租约代次、重复序号、过期 permit、入队后超期、队列满急停、STA/WSS 断线、操作者冻结但 WS 保持、重连无动作恢复、本地 AP owner 不受云断线影响、拥塞限流和配置仲裁。Node 可使用临时测试证书覆盖它自己的 TLS 校验；没有板端运行就不能声称已完成 ESP32 实际公网握手、堆峰值或控制延迟验收。

## 4. V3 归档与 V4 发布

根代理已在开始改变当前固件前建立 `versions/v3.0/CombatBot_V3_Release`，来自 `be7bbf064942eed2942e98a5827459e7b4a75449`，按完整仓库结构保留 123 个文件，排除 `versions/`、`planning/` 及不在 Git 中的缓存/产物，已登记并核验 V1/V2/V3 的历史哈希。本清单仅记录其完成状态，未改动历史快照。

当前 `package_history.py` 的归档说明假定入口为 `<base.name>/<base.name>.ino`，适用于 V1/V2，但不适合完整 V3 根目录快照。SOURCE_MANIFEST 的 V3 条目已加入 `arduinoSketch: CombatBotArduino/CombatBotArduino.ino`；打包说明必须读取并校验该字段，旧条目缺省仍采用现有规则。V3 包的实际打开位置应为 `CombatBot_V3_Release/CombatBotArduino/CombatBotArduino.ino`，不能再猜测不存在的 `CombatBot_V3_Release.ino`。历史内容按原始字节归档，扩写和勘误放 `docs/releases/V3.0.md`，不能修饰归档源码。

V4 的 `VERSION`、固件版本、包名、发布说明同步为 4.0.0 / V4.0；README 在完整更新记录最上方追加 V4，V1/V2/V3 展开内容持续保留。新增 `docs/releases/V4.0.md`、云部署说明、协议与迁移说明、软件验证报告，明确哪些能力新增、哪些继承、哪些需要现场校准。

最终仍通过 `python tools/package_history.py` 发布整个工程：先核对当前 V4 全部新凭据，再收录 V1/V2/V3，校验每个历史来源、ZIP CRC、manifest SHA256，生成当前和历史独立下载入口。旧 tag 不移动、不强推；服务器部署目标未确认前仅提供可运行的服务端工程及部署模板，不操作现网。

## 5. 实施启动前的剩余决策

1. 公网域名、服务器位置、HTTPS/WSS 路径与实际部署授权。
2. 单车/多车、操作者身份与每车 viewer/controller 权限。
3. STA 保留 AP 后的明确接管规则，以及远端解锁、配置、重启是否开放。
4. 自主格斗在云失联时是否继续、由谁续比赛许可、怎样本地取消。
5. 板载 Flash 与最终分区；依赖加入后的真实容量和板端 TLS 内存边界。

这些决策影响协议与安全门控，不能靠网页默认值偷偷替用户决定。
