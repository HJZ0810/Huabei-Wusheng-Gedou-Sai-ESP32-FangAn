V2.0 沿用 V1 的整车功能和 Arduino 平铺结构，集中补强停止投递、客户端抢占、非法输入、换向及传感器异常等路径。它让“多个页面、队列积压、读数异常时怎么办”成为显式的软件规则，而不只依靠正常操作流程。

这一阶段先有 [71b97c9 融合提交](https://github.com/HJZ0810/Huabei-Wusheng-Gedou-Sai-ESP32-FangAn/commit/71b97c9)，再以 `fd650ac` 作为 V3 比较和本页恢复的最终公开基线。本地后来修改的同名工程不属于这里的 V2；各版本变化以对应提交源码为准。

## 从 V1 延续的完整能力

V2 保留常驻 AP、可选 STA、mDNS 和强制门户；内嵌可编辑网页使用 WebSocket 遥测与 REST 设置/动作接口。驾驶支持连续摇杆差速、定点距离、定点转角，页面可观察速度、里程、姿态、电池、六路红外、灰度/E18、状态和进度。

四轮 PWM/DIR、FG 反馈、速度闭环、梯形行程规划和航向修正继续存在；转向采用轮行程主转及 IMU 精修。IMU 零偏、K_odo 行程和 K_turn 转向标定均保留，舵机提供中位、举铲和放铲。配置仍以 JSON/NVS 管理，支持分组更新、导入导出和默认参数。

电池低压限速、严重低压停机、堵转、可选边缘和红外保护也延续。V2 原始独立保护开关默认开启；这些默认值并不证明未知接线和未知电池体系下已经可安全使用。

## 相比 V1 的主要加固

| 改进 | 具体实现 | 工程收益 |
|---|---|---|
| 停止绕过普通队列 | stop/estop 递增原子代次并置 pending 标志；控制任务先消费停止，再读普通指令 | 队列容量不会直接丢掉停止请求，旧代次动作不继续执行 |
| 单一控制权 | 用原子 CAS 将 owner 从 0 改为客户端编号；连续模式允许本人刷新 | 两个连接不能同时成功申请空闲控制权 |
| 控制者断线处理 | WS 断开只对当前 owner 请求停止；心跳只认 owner | 旁观者单纯断开不再通过服务端直接打断运动 |
| REST 纳入仲裁 | REST 使用合成编号 `0xFFFFFFFF`，WS 编号 0 表示无人 | REST 不再绕开已有的连接控制权规则 |
| 动作与输出校验 | 指令检查有限数、类型及距离/角度/速度范围；电机出口对坏输入撤驱动 | 避免明显异常数进入控制计算和 PWM 输出 |
| 配置范围收口 | JSON 合并后统一限制机械、运动、PID、舵机和安全参数，修正部分交叉关系 | 减少小数点和范围误填；NVS JSON 读取也经过同一合并路径 |
| PCNT 优先计数 | 探测 legacy PCNT，启用硬件滤波；初始化失败回退 GPIO 中断 | 将可用通道的脉冲计数交给硬件，保留降级路径 |
| 换向保护 | 先撤 PWM，距末次 FG 边沿至少 120ms 且速度不高于 0.8cm/s 才换方向 | 减少满速反向驱动的机械与电流冲击风险 |
| PID 首拍和积分 | 首次采样不做差分；仅未饱和或误差有助于退出饱和时接受积分 | 降低复位微分突变与持续饱和的积分积累 |
| 零偏窗口 | 显式采样加入方差检查；在线自适应用独立内存增量，限制在标定值 ±0.1°/s | 减少抖动污染标定及在线偏置无限漂移 |
| 逐通道有效性 | IR 电压范围、电池有效性、IO 在线与扫描时间戳进入数据结构；无效 IR 发送 JSON null | 页面显示 `--`，无效通道不冒充真实距离 |
| 按方向限速 | IR 只检查与行进方向夹角不超过 60° 的通道；原地转向全向检查 | 避免车尾贴墙时所有前进动作都被同样限制 |
| 配置编辑门控 | 动作繁忙时拒绝普通配置 POST，保存期间使用 hold 状态 | 明确阻止正常动作中随意切换控制参数的意图 |
| 资料补充 | 新手 Arduino 环境指南与融合版验收项目 | 安装、接线和异常操作有可追踪检查入口 |

这些属于 **V2 已有能力**。V3 继续保留、调整它们，不能把急停旁路、CAS、PCNT、换向等待和条件积分再作为 V3 首次发明的功能。

## 这一版的优势

- **停止和普通动作有明确优先级。** 代次使停止能够同时废弃队列积压，而不仅是队尾再放一个停止。
- **多客户端规则开始完整。** 动作占用、本人续命、本人断线和 REST 来源统一进入仲裁。
- **输入到输出都有校验。** 网络指令、配置合并、PID 和电机输出分别设置基本防线，错误不再只依赖 UI 控件避免。
- **异常读数更诚实。** 逐路有效性通过 null 告知页面，有效值、无数据和超时状态不再全部混为数字。
- **机械保护有可读条件。** 换向静默时间、速度阈值和非阻塞等待写在电机模块内，可按真实 FG 和惯性继续验收。
- **沿用易读的工程结构。** 平铺模块、中文注释、PROGMEM 网页源及 [原始文档索引](../../versions/v2.0/CombatBot_Fusion/docs/README.md) 让学习和维护入口保持连续。

## 仍然存在的边界，以及 V3 为何继续改进

V2 完成的是重要的基础加固，但多个局部保护组合后，仍有需要继续验证和修补的路径。

| V2.0 公开基线边界 | V3.0 的改进方向 |
|---|---|
| 连续速度 0 被当成满速比例，电气取反会改变逻辑反馈符号 | 零目标速度语义、逻辑反馈与电气输出分离 |
| 航向修正左右输出符号及整圈角度折回存在问题 | 统一轮序/偏航负反馈，累计多圈偏航 |
| 位置 PID、turnAccel/turnDecel 没有完整用于动作运算 | 实际位置闭环和角加减速，独立转向轮行程标定 |
| 条件积分仅观察 PID 自身限幅，之后仍叠加前馈和电机补偿 | 按最终 PWM 可用范围处理积分，换向等待清积分 |
| PCNT 通道按 `i % 8` 配置；S3 部分轮会使用不支持的通道号并回退 | 四轮分别使用 S3 四个单元的合法通道，覆盖失败和回卷路径 |
| 心跳停机只应用于连续模式，异步刷新时间可能晚于当前周期起点 | 全运动模式心跳及近期未来时间戳、回绕处理 |
| REST 客户端共享一个合成编号，不能证明对应某个 WS 控制者 | 用随机连接令牌将 HTTP 与实际 WS 会话绑定 |
| 服务端旁观者断开已过滤，网页生命周期仍可能自动发全局 stop | 网页自动停止仅由本人的待受理/运行动作触发 |
| 配置 hold 与命令消费未形成完整共享仲裁，NVS 写结果未确认 | 等输出撤除后编辑，写成功才发布配置 |
| 舵机使用 S3 不支持的 16 位 LEDC 配置，初始化失败未充分门控 | 14 位舵机 PWM 和绑定结果检查 |
| IR 无效即跳过，限速比例为固定档；新方向未充分覆盖轮子余转 | 渐进限速、无效策略及输入/目标/实测方向联合保护 |

方差检查能够排除部分抖动，不能单独证明车辆静止：匀速运动可能仍有低方差。PCNT 回退存在不等于所有轮都始终使用硬件计数。扫描时间戳存在也不等于每个失效分支已完全门控。停止请求的及时受理不能证明车体已经立即静止；软件撤 PWM 与主动制动是不同的硬件能力。

## 历史验证记录与证据边界

原始材料没有在本次恢复中新增对应的完整成功日志、源码哈希或上板数据。历史依赖、工具链或配置变化后，必须重新编译和验证，不能把 V3 通过的回归套用于 V2。

V3 的优势之一是提供绑定发布源码的回归、双版本构建日志及交付核验；相应结果见 [V3.0 发布说明](V3.0.md) 和 [当前验收与验证](../../验收与验证.md)。这补齐的是软件交付证据，不是实车安全或量产证明。

## 升级、回退与后续维护

V2 配置使用 `cbot` NVS 命名空间，V3 使用 `combatfusion`，不会自动加载或覆盖旧配置。升级前导出参数并保留 V2 源码/固件；按 [V3 迁移说明](V3.0.md#升级与回退) 核对 PID 单位、接口、舵机目标及六路 IR 的通道和安装角变化。V3 的保护总开关默认关闭，也不能按 V2 开关默认值推断 V3 已启用全部保护。

保留 V1、V2 的完整源码和历史说明后，后续版本应在首页更新记录顶部追加新项，并继续链接各版本说明。历史内容可以补充勘误和证据边界，但不应被新版本简介替换；这样才能看到能力从完整链路、基础安全加固，逐步演进到运动正确性和可验证交付。
